# Synthetic irregular moons through the catalogue propagator

Original implementation read at `d1b5e33`; GPU follow-up read at `97a73e3` (initial `git merge rc`: already up to date). The fixed moon trajectories disagreed with NORTH_STAR §3.5; the frame/unit/provenance/light-time contracts were consistent. The physical law follows that contract and the sourced system GMs, not a validation score.

## Model and representation

435 Jupiter and 23 Saturn draws use two system-barycentric instances of `SmallBodyField`. Each reuses the existing step shader, float64 CPU twin, 65-sample ephemeris table, epoch grid, checkpoint planner and partial display step. The central monopole is the host system GM. Perturbers are the Sun and every catalogue perturber except the host (including the Earth/Moon split and Pluto system already in that list). Every kick is differential, direct minus indirect. Solar 1PN, Earth J2 and non-gravitational terms are disabled in this translated frame. Internal satellites are included only through the system monopole; their resolved forces and host J2 remain omissions.

The product stores f64 ICRF epoch states **beside the original f32 elements**, in each population's sourced `integration.initialState.value` array indexed by `firstObject + k`. They are computed from the elements after f32 storage rounding, with the original system GM and obliquity, and serialized as round-trip f64 JSON numbers. The element binary stays unchanged for identities and inspection; this small 21,984-byte numeric payload for 458 states avoids adding six Cartesian columns to three million heliocentric records. Both CPU and GPU use this shared serialized initializer. Identity, ordering, seed, counts, H/attributes, cells and epoch are unchanged. The private rebuild's `objects.bin` SHA256 is `61d7c0a4ef1e6850688588d1308bfd689550b980b87e6ce8218b4dc375411fdc`; `cells.bin` is `215040deedf1a30cdda2b50dbe0fe2e004809628c65edc7f079846876f47e56e`; both equal the shared snapshot captured before this lane's change. After merging root's CFEPS veto, the final binaries are `98017c0a31011331893592f87e37c4734bcd4e9cf43f2fb1e2cd119c71b86c14` and `0ba000d6cdcfc4bc01a017b4813246e0356932454be29cefcd38abcfe08960a0`, equal to root's corresponding rebuilt shared binaries. The root change removes 143 heliocentric TNO records and shifts global moon rows; this lane preserves all moon states and adds no element/cell changes.

The existing free-form `populations[].model.integration` dictionary records version `host-smallbody-v1`, window, translated force model, input product SHA256s and separate budgets. The stage directly depends on ephemeris products so those hashes participate in rebuild decisions. No schema extension or new raw input is needed. Both GPU and CPU consume that product law. Missing metadata, coverage or failed propagation gives unknown motion, never fixed-element fallback. Epoch initialization can still be inspected when the law is missing. Selection, travel and fallback picking use `syntheticState`; GPU picking consumes the same integrated trajectories' shaded records. The existing `syntheticRelativeState` function remains the **osculating ellipse guide** for orbit overlays, not a moon trajectory away from the epoch. Heliocentric synthetic draws still use fixed Kepler; that separate §3.5 defect is unchanged.

The two batches expose their integrated host-relative display states internally, retaining double-single components through camera/centre cancellation before the final f32 direction. The synthetic shade pass preserves original row IDs, H-G law, synthetic labels, Complete gating and first-order SSB-velocity light time. The system barycentre's geometric position and velocity are added, not the physical planet centre's.

## Numerical evidence and limitations

The pinned all-moon fixture copies the landed lane's independently generated **Sun plus external planets** DOP853 endpoint states. Its source realization's rows start at 2969638; the fixture-capture build starts at 2969636 after a preceding population count change. The final merged CFEPS-veto build starts at 2969493; local moon ordering, counts and all epoch states still match. `referenceRow` and current `row` are both recorded. Every one of the 458 initial states agrees within 1e-7 km / 1e-13 km/s; no reference endpoint was fitted or regenerated to make the implementation pass. Input hashes for the reference ephemerides are in the original landed `synthetic_moon_reference.json` and the new fixture's provenance.

Before the implementation, 916 production edge comparisons had maximum **29,407,853.36 km** fixed-element error. After it, the maximum is **0.042165649 km**. The predeclared CPU numerical regression threshold is **0.1 km**, inherited from the translated candidate's documented 0.042166-km maximum. This checks both edges, not a continuous interval or true astrometry of an undiscovered object.

### GPU follow-up: arithmetic before changing the representation

Root's hardware run (NVIDIA Blackwell, lane `root-gpu/moons-earth.log` and `moons-close.log`) reported **45.500621 km GPU minus CPU**, **45.513762 km minus DOP853**, and **0 km selected minus CPU** at the first non-epoch sample (the far window edge). It aborted before recording the worst row or the other times. These are observed maxima for that run, not continuous bounds. The prior 2-km threshold copied from the catalogue report was unjustified and is retired. The physical-centre camera crashes were harness bugs: `loadEphemeris` loaded `de442s` and `sat-plu` but omitted `centers`, the product supplying physical 599/699 offsets. All camera modes now use the same checked helper and ephemeris inventory as their CPU regression.

* **State storage is not plain float32.** `field.ts` serializes f64 epoch states as `split64`, with 12 f32 per object (three high/low positions and velocities). `kernels.ts`'s `St`, RK4 stage position additions, central monopole acceleration and final RK4 central-force sums remain double-single. Moon and catalogue batches use precisely this layout, shader and debug readback. Moon origin is the host-system barycentre, not SSB; no hidden catalogue-only nearer origin or extra precision exists. A coordinate of 20 million km has a high-component f32 ULP of 2 km, but the low component preserves roughly another 24 bits: storage rounding is order **6e-8 km**, not 2 km. Plain f32 three-coordinate rounding could be order 1.7 km here, but that is **not** this implementation's state error.
* **Checkpoint spacing does not reset accumulated error.** Default H is 172800 s (2 days), C is 8 grid steps (16 days in these compact batches), and the display takes one unstored partial step of magnitude <H. Checkpoints copy accumulated double-single states; they do not upload a new exact CPU state. Finer checkpoint spacing alone should give the same arithmetic path, apart from restore/history issues. The baseline periods are **493–823 days for Jupiter**, **434–1292 days for Saturn**, with e up to **0.499 / 0.564**. Solar direct-force dominance exceeds the product's 0.001 RK4 switch in these states; the imported encounter step rule restricts central timescale steps to 0.01 sqrt(r_eff^3/GM). Expected substeps are hours to a fraction of a day, not a single two-day Kepler approximation. The f64 implementation's measured endpoint truncation error is **0.0422 km**, so shared scheme truncation cannot explain a GPU-only 45 km. A partial step has one interval's force roundoff; accumulated force bias grows roughly as t² before orbital response. The finer-grid diagnostic changes H to H/4 and therefore the table sample spacing to 11.25 minutes, with a matching f64 twin. Its CPU-versus-default differences are reported independently. It does not choose another physical model.
* **Float32 enters the external force.** `prel` rounds the double-single relative separation into a vec3f; `dot`, `inverseSqrt`, GM and the direct acceleration are f32. The separately computed indirect acceleration is summed in CPU f64, stored in f32, interpolated in f32, then added to the direct result. At a sampled Jupiter–Sun separation 765–813 million km, Sun acceleration is about 2e-7 km/s²; at Saturn 1387–1436 million km it is about 6.5e-8 km/s². With unit roundoff u=2^-24 and T=548.01537 days, **½ u a T² ≈ 15 / 4 km**. Several rounded operations and the cancellation between these large terms can therefore produce tens of km. The Sun's stored high-coordinate ULP is 64 km at Jupiter and 128 km at Saturn; losing bits in R−x affects the direct force even though the moon state itself is double-single. `substep_level` also uses f32 high positions/velocities, which may change a level near a threshold; comparison against a finer-grid f64 twin exposes the resulting differences.
* **Quantified force arithmetic, not a GPU certificate.** The CPU diagnostic transcribes explicit f32 operations for the Sun's direct-minus-indirect force at epoch and both pinned edges (1305 Jupiter and 69 Saturn moon states), compared with independently evaluated f64 differential force. Largest instantaneous absolute errors are **1.0244e-13 / 3.0760e-14 km/s²**. Holding those errors coherent for T gives **114.8 / 34.5 km** position scales. These are dimensional predictions, not integrated bounds: orbital feedback, changing force geometry, native GPU inverse-sqrt accuracy, compiler contraction and error correlations are excluded. They comfortably explain the scale of 45.5 km, but do not identify its worst moon or prove the dominant mechanism. Double-single central RK4 sums avoid an additional u×central-acceleration bias; its rounded h²a stage terms are far smaller (metres or below per stage). Catalogue bodies do not generally subtract a solar direct force from a solar indirect force: the Sun is their central double-single force. That change in cancellation conditioning, rather than state layout, explains why the catalogue's 1.6 km is not a moon budget.

The other predicted contributions are much smaller: a single <2-day display step with the largest transcribed force error contributes **<0.0016 km** via ½δaH², not 45 km. With η_enc=0.01, an RK4 stage's ¼h²a central term is ≤2.5e-5 r; its f32 rounding is ≤6e-8 of this, or **<0.00006 km** for the pinned r≤39.2 million km (six centimetres per stage). Central-force feedback on that error is of relative order uη², giving metre-scale coherent estimates, rather than tens of km. These are order estimates, not accumulation bounds. Table interpolation of sample *differences* has centimetre-scale errors (the existing catalogue table test reports <0.02 km); inserting a 0.02-km solar-separation interpolation error into 2aδR/R and integrating coherently gives **about 0.01 km** at Jupiter. However, f32 interpolation of the *indirect acceleration itself* can have order-u bias on the large solar acceleration, already included in the tens-of-km force scale. More table samples or checkpoints cannot restore those discarded force bits.

The **opt-in** `tidal` diagnostic evaluates the *same* external Newtonian law without subtracting two large rounded accelerations. For R=perturber−origin, x=moon−origin, q=(x²−2R·x)/R² and A=(1+q)^(3/2), use f=−q(3+3q+q²)/(A(1+A)) and a=GM/R³ [fR−(1+f)x]. This equals GM[(R−x)/|R−x|³−R/|R|³]; it changes neither GM, law nor omissions. For |q|≥0.5 the direct differential expression avoids a near-perturber loss in 1+q. CPU tests check signs, orientations, zero displacement, and a limiting displacement too small for direct f32 separation to retain. Its same-sample f32 force errors are **7.6112e-15 / 1.2063e-15 km/s²**, giving coherent scales **8.53 / 1.35 km**. These are expected improvements for root to falsify, not a claim of achieved GPU accuracy. Production and the catalogue leave this branch disabled. The baseline, finer grid and tidal variants all retain double-single state.

### Perceptual numerical allocation

The angular policy is **min(0.1/(2R_max) degrees, 0.1 centre-pixel angular pitch)**, where R_max=17.25 π/2+25.72=52.816 cycles/degree is the brightest-limit asymptote of the app's cited Ward Larson et al. (1997) / Shlaer (1937) acuity fit (`eye/acuity.ts`, `eye/constants.ts`). A tenth of its smallest resolvable half-cycle reserves nine tenths for other errors and is stricter than display sampling here. This is a conservative numerical allocation, **not** a universal threshold for vernier astrometry, enhancement, magnification, object visibility or total model uncertainty. At the app default **50° vertical field, 1280×720**, the limit is **3.408043 arcsec = 0.012756 centre pixels**. Angles are computed with atan2(cross,dot), so sub-arcsecond differences do not disappear in acos rounding. The harness asserts this angle separately for each camera's actually rendered ray, also reporting geometric state and apparent-state angles. Narrower fields / larger viewports apply the pixel cap.

For a hypothetical **transverse 45-km** displacement, the pinned epoch/edge geometries give the following angular envelopes (arbitrary displacement orientation reduces them). Pixels are centre-pixel equivalents θ·720/[2 tan(25°)], not a frustum projection or a rendered-scene result:

| Host and observer | Arcseconds | Centre pixels |
|---|---:|---:|
| Jupiter physical centre | 0.2373–0.8767 | 0.000888–0.003282 |
| Jupiter moons from Earth | 0.01018–0.01447 | 0.0000381–0.0000542 |
| Jupiter physical centre + 10 sourced equatorial radii along ICRF z | 0.2348–0.8764 | 0.000879–0.003280 |
| Saturn physical centre | 0.2795–1.3754 | 0.001046–0.005148 |
| Saturn moons from Earth | 0.005787–0.007492 | 0.0000217–0.0000280 |
| Saturn physical centre + 10 sourced equatorial radii along ICRF z | 0.2762–1.3559 | 0.001034–0.005075 |

The planet-to-camera offset is not the observer-to-moon distance: most irregular moons are millions of km away even from the 10-radius camera. An observer 10 km from a moon is a separate stress test; a 45-km transverse error there is atan(45/10)=**77.47°**, which must fail this budget. The harness reports close-view failure after saving all evidence. Real close-view apparent distance also includes the shared first-order light-time displacement.

The double-single representation can retain about **0.1 mm** at these state magnitudes; it does not impose a 2-km floor. Final f32 normalization gives a direction-rounding scale around **1e-7 rad = 0.021 arcsec = 0.000077 centre pixels**. Neither is a guaranteed minimum attainable error (exact/parallel differences can be zero). With current f32 forces the coherent instantaneous-error scales above predict kilometre residuals even with finer checkpoints; reducing force cancellation can approach the finer direction/storage limits, but only the hardware run can establish the achieved floor. The present 45.5 km may already be imperceptible from all three requested cameras; that does not certify arbitrary close views or justify transferring the catalogue's km threshold.

Inspector text separates numerical checks, historical force increments and unknown individual true-position/covariance/current-view total error. The preceding motion lane measured Sun+host trial increments, independently: Jupiter J2 168.915 km, resolved planet/Galileans 342.042 km; Saturn J2 144.471 km, resolved planet/Titan 762.623 km. These are sourced historical **individual sampled increments**, not their sum or an omitted-force bound on this Sun+external-planet model. Other satellite masses/higher zonals, radiation pressure and relativistic frame effects are unbounded. External catalogue perturbers are now included, so their previously reported omission increments are not charged as current omissions. No own-disk, arbitrary-close-view or interval certification is claimed.

## Cost and device checks

The private in-process CPU benchmark uses `process.cpuUsage`, 100 repetitions: all 458 stored epoch-state reads average **0.17194 ms**, building a new two-day table interval for each of the two hosts averages **0.51858 ms**. Reused intervals need no new ephemeris sampling; this does not assign zero cost to cache lookup/API encoding. These measurements exclude shader compilation, uploads, command encoding, GPU work and catalogue work. The earlier candidate's first full two-day step counts 1,299 RK4 substeps / 5,196 force evaluations. There are eight workgroups across the two hosts. Ordinary frames use one partial display step per host plus any crossed grid steps; jumps/restores and background building add work. `moonBatchInfo` records actual planner steps, restores, state/checkpoint and table bytes, and CPU **wall** time separately.

The original implementation required a `synthetic` rebuild; root has synced that product. This follow-up changes no data product: **no rebuild or new download** is needed. Run once from `app`:

```bash
node scripts/sb-gpu.mjs --gpu hardware --query 'mode=moon-compare&timestamps=1' --json out/moon-comparison.json
```

It reports baseline / fine-grid (H/4) / tidal (same H) sequentially in one JSON, every moon at epoch, signed offsets through ±365 days with 12345-s partial steps, both exact edges, repeated far jumps and final epoch restore. Each variant has maximum, nearest-rank 90th percentile and worst moon id/time for position, velocity, reference endpoints and all three angles. Per-time summaries and per-moon signed delta-km vectors expose growth and restore differences. Each time shades Earth plus both planets and both 10-radius cameras. The GPU/CPU comparison uses the variant's own f64 grid; `defaultCpuKm` and `cpuGridChangeKm` keep finer-grid differences visible. Selection is checked against unchanged production CPU motion. Numerical/identity failures are collected: JSON is written **before** the runner exits 1. An unknown state or unavailable required product remains a fatal failure.

Switch with `variants=baseline,fine-grid,tidal` (or any subset), `gridDivisor=2|4|8` (fine-grid only), `checkpointSpacing=1`, `repeats=16`, `fov=50`; `syncam`/`camera` choose an additional timed/rendered camera, independently of the three per-moon own-host views. The baseline should reproduce the scale of 45.5 km; finer-grid-only improvement tests grid/interpolation versus force bias, and tidal improvement tests cancellation. ## Production follow-up

The later `root-gpu/moon-comparison.json` hardware run measured stable tides at 1.941 km maximum / 0.416 km p90 GPU minus CPU, 1.944 km versus DOP853, and rendered maxima of 0.028/0.028/0.022 arcsec for planet/10-radius/Earth cameras (3.408-arcsec budget). Production kernel and f64 twin now use that algebra; baseline remains a named diagnostic. Catalogue solar gravity is central and has no cancelling differential solar kick. The null picks came from the page's stale camera rays: it shaded other cameras after saving the requested direction. The page now restores the camera and reads live records; `mode=moon-pick&timestamps=1` samples each host every tenth moon at epoch and both edges plus a catalogue control. This follow-up **requires a synthetic rebuild for metadata**; it supersedes the earlier no-rebuild/unverified statements. Root ran both commands on the workstation's NVIDIA Blackwell GPU on 8 October 2026 with the stable form as production. `mode=moon-compare`: every variant inside the budget at every camera (baseline 51.754 km and 0.678 arcsec, fine grid 53.721 km, stable tides 1.941 km and 0.028 arcsec), no failure. `mode=moon-pick`: 144 of 144 picks return the expected index (47 sampled moons and the catalogue control, at the epoch and both edges of the window). At the page's first tolerance of 1e-7 rad, 3 of the 144 exact picks returned nothing; none did at 3e-7 or 1e-6: the pick pass compares squared chords in single precision, where a unit direction's own rounding is about 1e-7 rad, so the proof now asks for 1e-6 (the app itself picks within 6 pixels). No defect was found in the product's picking of synthetic moons. Omitted-force, interval and arbitrary-close-view budgets remain unknown.
